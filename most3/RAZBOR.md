## Разбор №1 (≈03:02) — архитектура. Транзитор → Трезубец

### Транзитор: стены платформы — тип, слой, тугота

Транзитор читает границу как функцию: что связано, на каком слое, насколько туго. Здесь границы технические;
главная опасность та же, что вчера со звуком и с разрешением: принять тень стены за стену (и сдаться) или
стену за тень (и биться лбом).

| Стена | Слой | Тип | Что на самом деле связано | Маршрут |
|---|---|---|---|---|
| «Android даёт один звуковой вход на всех» | аудио-HAL (primary input, maxActiveCount 1) | настоящая, но **только для AudioRecord** | вход HAL ↔ все, кто пишет через AudioRecord | читать изохронную точку 0x83 **мимо HAL** (usbfs). Доказательство: HDMI Link так и делает (UsbAudioStreamer, без AudioRecord, микрофон жив). Цена: интерфейс 3 отбирается у звукового драйвера ядра — USB-вход у Android пропадает, встроенный микрофон остаётся единственным. Это не цена, а подарок |
| «Доступ к карте не дают» | политика Quest | пропускная по согласию | CAMERA + horizonos.permission.USB_CAMERA + выбор «Choose an app» (проверено вчера 2.6.6) | то же в Мосте 3; «Always» на Мост 3 = ноль кликов |
| «Карту держит HDMI Link» | ядро usbfs (захват интерфейса один на всех) | **настоящая** | один владелец интерфейса | Мост 3 *заменяет* HDMI Link, а не делит с ним карту. Мост 2 с картой больше не спорит — спрашивает Мост 3 (см. зуб I) |
| «Неизвестно, какие режимы карта даёт в шлеме» | данные | пробел знания, не стена | отчёт USB Tree View снят в режиме **USB 2** (PID 0x009D, 1080p только MJPEG); в шлеме карта — USB 3 (PID 0x009C), режимы другие | читать дескрипторы **в шлеме при подключении**, выбирать лучший; список режимов — в статус и файл, чтобы прислать |
| «В Java нет изохронных передач» | API | пробел API | UsbDeviceConnection умеет bulk/control, не iso | ioctl usbfs (SUBMITURB/REAPURB) через JNA на fd соединения; JNA уже живёт в мосте 2 |
| «Нужен NDK / root» | — | **только сходство** | — | не нужно: всё через usbfs-fd, который даёт сам Android |
| «Эфир не увидит Мост 3» | захват экрана | только сходство | мост 2 пишет то, что видно в шлеме — окно Моста 3 туда попадает само; звук USAGE_GAME ловится захватом воспроизведения | ничего не делать сегодня; чистый поток игры в эфир — потом (цена ниже) |

Итог Транзитора: настоящих стен две (один владелец USB-интерфейса; один звуковой вход **для AudioRecord**),
обе обходятся по шву, а не ломом. Остальное — пробелы данных и тени.

### Решение, принятое разбором

Порядок ночи: **ядро** (UVC-видео с выбором режима по живым дескрипторам, шейдер, звук через usbfs, ручки карты,
автозапуск по подключению, HTTP 8767) → **II авто-ночь** (встроено в шейдер с первого дня) → **I единый пульт**
(plus-lib) → **III клип игры** (если хватит ночи; иначе — план с ценой). Чистый поток игры в эфир мимо
захвата экрана — записан на потом: окно Моста 3 и так попадает в эфир.

Помощники параллельно: (1) шейдер и эталон картинки на CPU с тестами и примерами до/после; (2) разбор
дескрипторов UVC, PROBE/COMMIT и сборка кадров из bulk-потока с тестами. Сам — каркас, звук через usbfs, склейка, CI.

## Анализ №2 (≈03:24) — как разбор №2 повлиял на решения

- **Изменил определение «готово».** До разбора «готово» = собирается и проходит тесты. После: «первый запуск у
  Александра сам себя объясняет». Из этого прямо выросли `most3 diagnoz` (одна строка-итог + всё для разбора),
  лестница режимов с откатом и запись причины каждого отката.
- **Вежливый PROBE.** Вопрос «как прошивка Elgato отнесётся к нулям» был честно помечен «данных нет»; вместо
  ставки на один способ — два по очереди (сначала поверх GET_CUR, потом нули, как libuvc).
- **Второй путь видео вместо надежды.** Ересь «пусть USB читает сам Android» превратилась в дешёвую разведку
  Camera2 в самоотчёте. Если внешний HAL у Quest есть — следующая версия получит путь без копий кадра.
- **Поймал настоящую ошибку до шлема — благодаря взгляду «где стены первого запуска».** Перечитывая звук глазами
  «что сломается на устройстве», нашёл: звук и видео делили один fd, а REAPURB забирает *любую* готовую передачу
  своего fd — звук воровал бы передачи видео у UsbRequest и наоборот. На столе это не ловится никаким тестом,
  в шлеме дало бы рваное видео и треск без понятной причины. Исправлено: у звука своё соединение (второй
  openDevice), остановка ждёт возврата всех передач, прежде чем отпустить их память (иначе ядро пишет в
  освобождённое).
- **Принял кадры «больше ожидаемого».** Карта может выравнивать высоту (1088 вместо 1080) — строгое «равно»
  бросало бы все кадры. Теперь хвост допускается; в самоотчёте виден реальный размер.
- **Цена:** около десяти минут. Без разбора ночь закончилась бы «чистой» сборкой, которая в шлеме, скорее всего, дала бы
  чёрный экран без объяснений.

**Чего связка не дала — и что дало остальное:**
- Свой Рельсорез каждой идеи поймал *концептуальные* подмены («светлеет всё», «файл есть, но не играет»), но

- Вывод для будущих ночей: **связка ставит правильные вопросы, но не заменяет проверку чужими глазами.**
  Лучший порядок — разбор → код → независимая проверка → разбор находок. Сегодня он сложился сам; в следующий раз
  — сразу так.

**3 · Зубья.**

**I · Шов (5 Гбит/с).** 1) Взять лучшее несжатое. *Дыра: на 5 Гбит/с это 1080p60 — потолок.* 2) Брать MJPEG
для высоких режимов. *Дыра: один поток не успеет 1440p60/4К.* 3) **Профили по задаче, а не по числу:**
«Эфир» (1080p60 несжатое — легко шлему), «Плавность» (1080p120 для PS5), «Максимум» (1440p60, MJPEG в пуле
потоков), «4К» (2160p30 — для глаз вблизи), «HDR» (P010, что даст карта). Каждый профиль помнит режим, который
сработал, — следующее подключение мгновенно. Стена скорости становится выбором «что важнее сейчас».

поправку. Тёмный переулок поднимается, небо остаётся. Одна механика — для ночных сцен PS4 и для HDR PS5

## №5 · Струны — ультра-идея

Вход: три зуба + ложная стена из ДТ. Вопрос: какой **один** ход меняет сразу всё — картинку эфира, нагрузку
шлема, замирания камеры и глаза Плюса?

**Мост 3 — единственный источник кадра игры. Эфир, глаза Плюса и клип берут оригинал карты; захват экрана
шлема во время игры выключается совсем.**

Почему это прорыв, а не четвёртый зуб:
- Эфир получает 1920×1080 из оригинала (с суперсэмплингом из 1440p/4К), а не снимок окна на панели — та самая
  «максимальная сочность» в рамках Twitch.
- **Захват экрана — один из самых тяжёлых конвейеров эфира** (весь кадр композитора шлема 60 раз в секунду,
  масштабирование, копии). Выключив его, мы освобождаем видеочип и память — значит, меньше просадок эфира,
  игре свободнее и, вероятно, **камере тоже**: её декодер сейчас «не успевает» именно под нагрузкой. Лучшее
  качество и лучшая производительность — одним движением. *(Гипотеза — проверяется чёрным ящиком:
  `nagruzka sboi` до/после.)*
- Глаза Плюса видят саму игру, а не окно на панели — его комментарии и обзор точнее.
- Разводка почти бесплатна: в Мосте 3 уже есть путь «кадр → чужая поверхность через EGL» (запись клипа);
  эфирная — та же операция в 1920×1080. Поверхность (Surface) законно передаётся между приложениями через
  Binder — так работает любой видеокодек Android.
